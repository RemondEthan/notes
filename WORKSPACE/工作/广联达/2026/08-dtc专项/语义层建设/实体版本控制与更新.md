# 实体版本控制与更新机制（含示例）

> 适用版本：OpenMetadata 2.0.4。回答：版本号怎么定、怎么涨、旧版本去哪了、并发更新怎么办。
> 配套 [mcp-create-entity-storage.md](MCP创建实体存储结构.md)（存储结构）、[mcp-create-entity-code-flow.md](MCP创建实体代码流转.md)（创建链路）。

## 1. 规则速查

| 时机 | 版本 | 代码 |
|---|---|---|
| 新建实体 | **0.1** | 固定初值（`EntityUtil.java:693` 注释示例 `table.version.0.1`） |
| 更新且字段有变化 | **+0.1**（0.1→0.2→0.3） | `EntityUtil.nextVersion` |
| 更新且发生**结构性变更** | **+1.0**（0.3→1.3） | `EntityUtil.nextMajorVersion` |
| 更新但内容完全相同 | **不变**，不记快照，不发事件 | `updateVersion` 返回 false |

版本判定在 `EntityRepository.updateVersion`（:9938）：

```java
if (majorVersionChange)    newVersion = nextMajorVersion(oldVersion);  // 结构性：+1.0
else if (fieldsChanged())  newVersion = nextVersion(oldVersion);       // 普通：+0.1
changeDescription.withPreviousVersion(oldVersion);
updated.setVersion(newVersion);
```

`majorVersionChange` 由各实体的 updater 在**数据型/结构字段**变化时置位（典型：table 的列增删、列类型变更）。glossary/domain 这类元数据编辑基本都是 minor。

## 2. 一次更新内部发生什么（5 步）

1. **取旧文档**：按 id 读 `json` 列（当前版本）。
2. **diff**：`EntityUpdater` 逐字段比较 original vs updated，产出 `ChangeDescription`：

```json
{
  "previousVersion": 0.2,
  "fieldsAdded":   [],
  "fieldsUpdated": [ { "name": "description", "oldValue": "旧描述", "newValue": "新描述", "changeType": "MINOR" } ],
  "fieldsDeleted": []
}
```

3. **定版本**：按 §1 规则 +0.1 或 +1.0（无变化则到此为止）。
4. **替换当前文档**：新 JSON（新 version + 内嵌 changeDescription）整体替换 `json` 列（`dao.update`）。
5. **旧版本快照**：把更新前的完整实体 JSON 写进 `entity_extension`（`writeBulkVersionHistory`，EntityRepository.java:7181），
   `extension = "<entityType>.version.<旧版本号>"`，主键 `(id, extension)` —— 一个历史版本一行。

## 3. 完整示例：glossary `Finance` 的一生

### T0 — `create_entity` 创建

```
glossary_entity : 1 行，json.version = 0.1
entity_extension: （无历史）
```

### T1 — `patch_entity` 改描述

请求：`patch = [{"op":"replace","path":"/description","value":"财务域核心术语表"}]`

- diff 发现 description 变了 → minor → `0.1 → 0.2`
- `glossary_entity.json` 被替换：`version=0.2`，内嵌 changeDescription（previousVersion=0.1）
- `entity_extension` 新增一行快照：

| id | extension | json |
|---|---|---|
| `3c4083b9...` | `glossary.version.0.1` | `{...0.1 时的完整实体文档...}` |

### T2 — 再补标签（`add /tags`）

- `0.2 → 0.3`，又一行：`extension = glossary.version.0.2`

此时数据库全景：

```
glossary_entity : 1 行，json.version = 0.3，changeDescription 记录 0.2→0.3 的 diff
entity_extension: 2 行（0.1、0.2 两份历史快照）
GET /v1/glossaries/{id}/versions       → [0.3(当前), 0.2, 0.1]   （快照前缀枚举 + 当前）
GET /v1/glossaries/{id}/versions/0.1   → 读 extension='glossary.version.0.1' 那行
```

**注意**：`json` 列永远只有最新一份，历史全在 `entity_extension`；表上没有 version 列。

### T3（major 示例）— table 改列类型

`table` 实体的 updater 检测到列类型变更 → `majorVersionChange=true` → `0.3 → 1.3`。
（对 glossary/domain 等元数据实体，日常编辑都是 minor，遇不到 major。）

## 4. 并发控制

两条路并存：

| 路径 | 行为 | 代码 |
|---|---|---|
| 带 expectedVersion 的更新（导入/批量等） | **乐观锁**：`UPDATE ... WHERE id=:id AND JSON_UNQUOTE(JSON_EXTRACT(json,'$.version'))=:expected`，影响 0 行抛 412 `"entity has been modified by another user"` | `EntityDAO.updateWithVersion`（:196）、`EntityRepository.java:5437-5444` |
| 普通 PATCH/PUT | **last-write-wins**：不比对版本直接替换；但因为每次更新前都写快照，任何覆盖都可追溯 | `store(entity, update=true)` |

## 5. MCP 工具视角

| 工具 | 版本行为 | 响应体现 |
|---|---|---|
| `create_entity` | 新建 → `version=0.1` | `_operation:"created"` |
| `patch_entity` | 有变化 → `+0.1`（或 major） | `McpResponseUtils.compactPatch`：额外带 **`version`** 和 **`changed`**（实际变更的字段名列表）；`_operation:"updated"` |
| `patch_entity`（patch 内容与现状相同） | 无 diff → 版本不动 | 无 `changed` 字段 |
| `create_test_case` 同名覆盖 | 旧用例相当于被更新 | `_operation:"updated"` |

`patch_entity` 响应示例（节选）：

```json
{
  "id": "3c4083b9...",
  "version": 0.2,
  "changed": ["description"],
  "_operation": "updated"
}
```
